Section 1

Executive summary

This report documents the design, implementation, and live findings of dune-resource-scanner, a Go tool that locates Dune Awakening raw-resource world positions by reading a live game server process's memory (/proc/<pid>/mem). The tool exists because the game does not track most raw-resource types (ore, stone, fiber) in its database at all — memory inspection is the only way to find their positions for the Live Map feature planned in dune-awakening-selfhost-docker.

What is proven

  • The tool's core scanning/validation logic is unit-tested (41 tests, 89.2% statement coverage of internal/memscan) and was independently proven correct against known ground truth: the tool's own class-identification output for two DB-confirmed resource types produced exact address matches against class pointers derived from an entirely separate scan method (§6).
  • Four real defects were found and fixed through live testing against the production-adjacent dune-dev host, each with an independent, reproducible root-cause diagnosis before the fix was written (§7).
  • A process/GRC defect was self-identified and corrected: Issue #1 auto-closed on a PR merge due to GitHub's literal handling of the word "Closes" in a PR body, contradicting the PR's own stated intent (§11.2).

What is not proven

  • Of ~28 distinct object classes found near the base's home island, only 2 have confirmed identity (spice, and a second DB-tracked resource informally called "mystery"). 26 remain unidentified. The strongest candidate for "Titanium Ore" matches the operator's stated in-game observation on count and spatial character, but this is candidate evidence, not proof (§8, §10).
  • A path to full identity resolution via Unreal Engine internals was considered and deliberately not attempted — see the risk analysis in §10.
How to read this report

Section 11 is structured so each reviewing discipline can jump directly to their area without reading the full technical narrative — but every claim there is backed by evidence in §5–§9. Use the sidebar to navigate.

Section 2

Scope & objectives

  1. Produce real-world positions for every raw-resource type in Dune Awakening (spice, an unidentified second DB-tracked resource, and 13 named ore/stone/fiber types with zero database tracking).
  2. Do so with a tool that is safe to run repeatedly against a live, player-facing game server: read-only, no continuous privileged process, no impact to server performance or availability beyond a bounded, on-demand scan.
  3. Produce output that can feed a future Live Map integration in dune-awakening-selfhost-docker (out of scope for this report — tracked separately in CONTINUATION.md).

This report covers steps 1–2 as executed against dune-dev (), the non-production development instance of the game server stack. It does not cover the Live Map integration itself.

Section 4

Methodology

4.1 Why a clean-room Go implementation

An earlier prototype (Python, third-party) was reviewed and found functionally useful but license-unresolved — no LICENSE file, no identifiable author, and the project's own NOTICE.md explicitly disclaimed redistribution. Because this tool is meant to be a permanent, recurring part of this workstream's tooling, it was rewritten from scratch based only on independently re-derived facts — not ported from, or written with reference to, the prototype's source. This resolves the license question for the resulting artifact entirely.

A secondary, independent reason to prefer Go: the prototype's byte-pattern searches were fast because they used a C-level primitive (bytes.find()); the new capability this rewrite exists for — scanning for a numeric coordinate pair near a known position across a multi-gigabyte heap — has no equivalent fast stdlib primitive in Python, and pure-Python loops over it timed out repeatedly. Go's compiled, statically-typed loops solve this directly.

4.2 Test-driven development discipline

All logic in internal/memscan was written test-first: a failing test was written and its failure verified before any implementation code. This produced 41 tests exercising:

  • /proc/<pid>/maps parsing and region classification — 12 tests
  • World-position plausibility validation — 5 tests
  • Byte-pattern and pointer-reference scanning — 11 tests
  • The full actor-shape validation chain, against a fake in-memory MemReader — 7 tests
  • The /proc/<pid>/mem I/O layer, against an in-memory stand-in — 6 tests

cmd/dune-resource-scanner/main.go (CLI wiring) was deliberately scoped as untested "thin glue" — stated explicitly in GitHub issue #1 before the code was written, verified instead by live testing against the real process.

4.3 Live-verification discipline

Every change went through a standard branch → PR → CI → merge cycle (Appendix A). CI runs build/vet/gofmt/test plus the organization's shared gitleaks + semgrep + trivy security-scan workflow on every push. All local commits were additionally scanned before being pushed. No commit in this investigation's history has a failing CI run on main.

5.2 The actor-shape validation chain

Unreal Engine game objects (AActor subclasses) have a predictable, low-level memory shape that can be validated without any engine symbols, by following a chain of pointers and checking each one lands in a plausible memory region. The chain, from internal/memscan/actor.go:42:

1
vtable pointerRead at the actor's own address — must fall inside the game binary's mapped image
2
ClassPrivate pointerRead at offset +16 — must fall inside a heap-like region
3
ClassPrivate's own vtableRead at ClassPrivate — must also fall inside the game binary's mapped image
4
RootComponent pointerRead at offset +576 — must fall inside a heap-like region
5
Transform (X, Y, Z)3 consecutive float64s at RootComponent +384 — must pass plausibility checks
func ValidateActor(mem MemReader, addr uint64, off Offsets, isExe, isHeap func(uint64) bool) (ActorInfo, bool) {
    vtable, err := mem.ReadU64(addr)
    if err != nil || !isExe(vtable) { return ActorInfo{}, false }             // step 1

    classPrivate, err := mem.ReadU64(addr + off.ClassPrivate)
    if err != nil || !isHeap(classPrivate) { return ActorInfo{}, false }      // step 2

    classVtable, err := mem.ReadU64(classPrivate)
    if err != nil || !isExe(classVtable) { return ActorInfo{}, false }       // step 3

    rootComponent, err := mem.ReadU64(addr + off.RootComponent)
    if err != nil || !isHeap(rootComponent) { return ActorInfo{}, false }    // step 4

    x, y, z := /* 3 consecutive float64 reads at rootComponent + off.Transform */
    if !ValidTransform(x, y, z) { return ActorInfo{}, false }                // step 5

    baseValue, _ := mem.ReadI32(addr + off.BaseValue)
    return ActorInfo{Addr: addr, X: x, Y: y, Z: z, BaseValue: baseValue, ClassPrivate: classPrivate}, true
}

Every one of the five gating checks must pass. This is the primary defense against false positives from coincidentally-matching byte patterns in a multi-gigabyte heap — §7's Bug 3 is a concrete case where getting one check (isExe) wrong caused 100% of otherwise-correct candidates to be silently rejected.

ValidTransform (validate.go:12) rejects: any NaN component, any X/Y magnitude greater than 1,250,000 (the world coordinate bound), and the exact origin (0,0,0) — the value an uninitialized/null actor reads as.

5.3 Memory region classification — two corrected assumptions

Two functions determine which regions are searched and which regions a discovered pointer is allowed to point into. Both were wrong in their first implementation and fixed after live testing exposed the error (full narrative in §7):

  • MainModuleRegions (maps.go:95) — every region backed by the same file as the main game binary (text and rodata and data), because relocated C++ vtables live in the read-only rodata segment, not the executable-permission text segment.
  • HeapLikeRegions (maps.go:116) — the classic glibc [heap] plus every anonymous writable mmap region, because Unreal Engine uses its own memory allocator, and [heap] alone was found to hold only ~3MB of a ~16.7–20GB total footprint.

5.4 Scanning algorithms

Seeded scan (FindInt32LE) — given a known numeric value (e.g. a spice tier's tracked quantity), finds every 4-byte-aligned occurrence as a little-endian int32, walks backward to a candidate actor address, and validates via §5.2's chain.

Proximity scan (FindNearbyXY + FindPointerReferencesMulti) — the genuinely new capability this rewrite exists for: given a known nearby world position and a tolerance, finds actors near it with no prior knowledge of any tracked value. Implemented as exactly two full sequential heap passes, independent of hit count:

  1. Pass 1 scans every heap-like region once for (X, Y) pairs within tolerance, collecting candidate RootComponent addresses.
  2. Pass 2 scans every heap-like region once more, checking every 8-byte-aligned value against the entire set from pass 1 simultaneously — instead of once per candidate.

This directly replaced a first implementation that re-scanned the whole heap per hit found — see §7 Bug 2.

Section 6

Evidence: ground-truth validation

This is the central proof point of the entire investigation: independent confirmation that the tool's class-identification is correct, using data the tool did not have when it made its original classification.

Step 1 — seed-mode scan

$ dune-resource-scanner -pid 3693040 -mode seed \
    -seeds spice-small=5000,spice-medium=150000,spice-large=2500000,mystery=60000

Result: 909 validated actors — spice-small=281, spice-medium=89, spice-large=6, mystery=533.

Evidence

The mystery=533 figure is an exact match to the "533-position pool" independently found in a prior session via a completely different method (direct SQL query against dune.resourcefield_state) — strong evidence the actor-validation chain finds the complete, correct population, not an approximation.

Step 2 — class pointers per label

Step 3 — independent cross-check

A separate, unrelated wide-area proximity scan centered on the player's base (-mode proximity -near -611736.35,-700183.46 -tolerance 100000) — which uses no seed values at all and works purely from spatial position — was grouped by ClassPrivate with no reference to the Step 2 table.

Result

Two of the independently-discovered class-pointer groups — 0x75c25f247290 (3 members, 82,906–98,725 units from base) and 0x75c26017b270 (3 members, 31,184–84,392 units from base) — are byte-for-byte identical to mystery's and spice-small's pointers from Step 2.

This is not a coincidence a broken or over-permissive validator could produce: ClassPrivate is a live heap pointer whose exact value depends on runtime allocation order, specific to this one process instance. Two entirely different search strategies — numeric-seed search vs. spatial-proximity search — executed independently, converging on the exact same pointer value for the exact same known object type is direct evidence the actor-shape validation chain (§5.2) finds real, correctly-typed objects, not an artifact of a loose heuristic.

Section 8

Findings: island survey results

8.1 Methodology note: tolerance semantics

FindNearbyXY's -tolerance flag is a per-axis box half-width, not a Euclidean radius: -tolerance 50000 searches a 100,000×100,000-unit box centered on -near, not a 50,000-unit-radius circle.

8.2 Base-part exclusion — a methodology correction

Self-correction

An intermediate analysis pass flagged several large classes (34–75 members) as "almost certainly base-building components" based on some instances having Z exactly 0.0. This claim was checked against its own premise and found false: those classes' closest member to the base is 11,000+ units away — far outside any building footprint. Retracted, not left standing. The actual base-building classes were separately confirmed via a genuinely tight -tolerance 3000 scan: 13 distinct classes, 1–2 members each, no overlap with the mis-flagged classes.

Preserved deliberately in CONTINUATION.md as a documented example of catching an unverified claim before it propagated further.

8.4 The Titanium Ore candidate — evidence and confidence level

0x75c268f7ade0 is the strongest single candidate for the resource type the operator described in-game ("at least 20, if not more" Titanium Ore nodes):

  • Count: 28 members within a clean, isolated distance band — directly consistent with "at least 20."
  • Spatial pattern: irregular, non-grid-aligned spacing, consistent with natural terrain placement.
  • Elevation: Z varies naturally across 867–5,141 with no suspicious exact values.
  • BaseValue uniformly 0 across all 28 — expected for a resource type absent from dune.resourcefield_state (§9).
  • A clean spatial discontinuity: after the 20th member (48,680 units), the next members of the same class appear only from 67,152 units — plausibly other Titanium deposits on distant islands.
Confidence level

This is circumstantial evidence, not proof. No independent verification (visual in-game check, or resolved class name) was obtained before this report was written. §10 documents why a further, riskier verification path was considered and rejected.

Section 10

Rejected approach: UClass/FName reverse engineering

To move the Titanium Ore candidate (§8.4) from "strong circumstantial evidence" to "proven," the tool would need to resolve the actual class name string from a ClassPrivate pointer. This was considered and deliberately not attempted — not because it seemed too hard, but for a specific, stated reason.

Unreal Engine resolves object names via FName, an index into a global name pool, rather than a raw string. Resolving one requires knowing, for this specific engine build:

  1. The byte offset of UObject::NamePrivate within the object header — not currently known.
  2. The FNamePool's block/offset encoding scheme — varies across engine versions, not confirmed for this build.
Risk analysis

The risk is not merely that this might fail — it is that a wrong guess at either unknown would produce a plausible-looking, confidently wrong class name, strictly worse for downstream consumers (including a future Live Map feature) than the current, honestly-labeled "unconfirmed candidate" status. An unverified inference is a hypothesis, not a fact, until independently confirmed against ground truth — and no ground truth exists here to verify a guessed FNamePool encoding against, unlike §6's validation, which had spice/mystery as independently-known-correct anchors.

Recommended path instead

A single in-game visual check of the closest Titanium candidate (X=−612311.21, Y=−708329.60, Z=4396.67, ~8,166 units from the base) would resolve this definitively in minutes — and, per pointer-neighborhood clustering already observed, would likely also resolve several of the other 25 unidentified classes at once, consistent with the BP_<Mineral>_Spawner / BP_<Mineral>_Pickup_[A/B]_Spawner / BP_<Mineral>_Component sibling-actor pattern found via string search in a prior session.

Section 11

Per-discipline assessment

Each subsection below is written to be readable independently by the discipline it names.

11.1 Security architecture

Threat model. The tool requires root-equivalent access to open /proc/<pid>/mem for a process it does not own. It performs reads only — no code in this repository writes to the target process's memory, calls ptrace(PTRACE_POKE*), or otherwise mutates target-process state. This was a design constraint stated before any code was written and holds throughout: the only I/O primitive used is io.ReaderAt.ReadAt.

Deployment model. A manual/scheduled host job, invoked over SSH, runs once, exits — explicitly not a continuous privileged sidecar container, matching a design constraint carried over from a prior security audit that rated hostPID + Docker-socket access as a near-trivial path to host root if compromised. This tool has neither.

Secrets handling. The tool's own output contains no secrets — actor positions and raw memory addresses have no value outside a live debugging session against this exact process instance (ASLR re-randomizes addresses on every restart).

⚠ Unrelated finding — flagged for awareness

While gathering the target PID via ps aux, the game server's ServiceAuthToken (a JWT, passed as a plaintext CLI argument in run-server.sh) was visible in full in process listing output, on every server-launch command line. This is a pre-existing condition unrelated to dune-resource-scanner — this tool did not create it and does not interact with it — but it matches this organization's own Requirement 24 ("secrets must not appear in logs, stdout, stderr, or process listings"). Not remediated as part of this investigation (out of scope); the token value itself is redacted from this report.

11.2 GRC / compliance

Evidence trail. This report, plus CONTINUATION.md and findings/2026-08-21-base-island-survey.json, constitute the durable evidence artifacts for this investigation. Every commit in Appendix A is independently reviewable; every PR ran CI before merge (§4.3).

Self-identified process defect

Issue #1 auto-closed on PR #2's merge because that PR's body contained the literal GitHub auto-close phrase "Closes #1" — despite the same sentence stating the issue should stay open pending live verification. GitHub's auto-linking does not parse qualifying language. Found while assembling this report, not by external review — reopened with an explanatory comment the same session it was found.

Risk classification. Every PR in this investigation stated an explicit risk classification (Low, in every case — read-only tool, no live-system state changes).

CI/branch discipline. All commits went through issue/branch/PR/CI/merge; none pushed directly to main. Branch protection requires all 4 CI checks plus blocks force-push and branch deletion.

11.3 Database administration

Access pattern. All database interaction used dune database sql "<query>". Recommended follow-up: confirm this wrapper connects with a role that has no INSERT/UPDATE/DELETE/DDL grants, matching this organization's stated convention of a scoped read-only role.

Queries executed (all read-only SELECTs):

  • SELECT id, map, name, dimension_index FROM dune.actor_spawners WHERE map = 'DeepDesert' ...
  • SELECT entity_id, components FROM dune.fgl_entities LIMIT 3 + a jsonb_object_keys(...) distinct-key enumeration
  • Standard schema introspection (dune database tables, columns)

No schema or data changes were made — no migration, INSERT/UPDATE/DELETE, or DDL of any kind.

Schema finding of general interest: dune.fgl_entities is a genuine ECS-pattern table (jsonb component bag) that DBA/architecture reviewers may not be aware of if primary schema documentation predates its introduction.

11.4 Software architecture

Design decisions and rationale are documented inline in §4.1 (language choice), §5.4 (two-pass algorithm), and above (deployment model: no sidecar, read-only, manual invocation).

Blast radius. Zero blast radius on the live game server beyond the CPU/memory cost of the scan itself (40s–2m20s observed per run). It does not modify game state, does not restart or signal the target process, and holds no lock or resource the server needs.

Algorithmic complexity, before/after the Bug 2 fix: the original scanProximity was O(hits × heap_size) — for a ~16.7–20GB heap and a wide-tolerance survey expected to find dozens of hits, this would re-read hundreds of gigabytes to terabytes per invocation. The fixed implementation is O(2 × heap_size), independent of hit count — confirmed by wall-clock time staying roughly constant (2m04s–2m34s) across scans finding between 15 and 533 actors.

11.5 QA / test

  • 41 tests across 5 files, all in internal/memscan (the package with all non-trivial logic).
  • 89.2% statement coverage of internal/memscan. cmd/dune-resource-scanner has 0% coverage by design (§4.2) — a stated, reviewed exception, not an oversight.
  • Every test written and confirmed failing before the corresponding implementation code existed.
  • Real command output was captured and checked at every stage of live verification — no claim in this report is asserted without a command/output pair backing it.

Recommended follow-up: parseSeeds/parseNear in main.go are simple but currently untested; a future session could add targeted unit tests for these two functions without violating the "thin glue" scoping of the rest of that file.

11.6 Network

This tool opens no network listeners and makes no outbound network connections of its own — all interaction is local (/proc/<pid>/mem, /proc/<pid>/maps on the same host) or via the pre-existing SSH channel used to invoke it. No new ingress or egress path, port, or DNS dependency. Not applicable beyond this note.

Section 12

Open questions & recommendations

  1. Resolve the Titanium Ore candidate's identity — recommended: a single in-game visual check (§10), not further memory-forensics guessing.
  2. Identify the remaining 25 unidentified classes — likely tractable in one pass once #1 is resolved, via pointer-neighborhood clustering.
  3. DBA follow-up: confirm the Postgres role used by dune database sql is genuinely read-only-scoped (§11.3).
  4. Security follow-up (out of scope for this repo, flagged for awareness): the ServiceAuthToken-in-process-args exposure (§11.1) should be triaged by whoever owns the server-launch tooling.
  5. QA follow-up: consider unit-testing parseSeeds/parseNear — low cost, closes a minor coverage gap.
  6. Once identity resolution covers a meaningful subset of resource types, design and implement the Live Map integration in dune-awakening-selfhost-docker per the design constraints already recorded in CONTINUATION.md.

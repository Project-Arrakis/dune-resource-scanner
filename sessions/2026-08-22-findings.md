## 2. `field_id` is a packed 21-bit coordinate triple — CONFIRMED

```
x =  id        & 0x1FFFFF
y = (id >> 21) & 0x1FFFFF
z = (id >> 42) & 0x1FFFFF
each: if v > 0xFFFFF: v -= 0x200000
```
Raw values are world units, no scaling. Verified against memory ground truth:
**spice 53/57 exact, flour sand 45/59 exact.**

**Implication: active resource positions come straight from Postgres. No memory scanner needed
in the Live Map data path.**

Must decode from string/BigInt — `field_id` exceeds `Number.MAX_SAFE_INTEGER`.

## Open items

- 14 of 59 active flour-sand fields decode to positions absent from the memory scan's 533 — the
  scan under-counts. Cause unknown. Not blocking (DB is authoritative).
- 6 `spice-large` memory hits look like false positives (grid-round coords, identical Z
  -4143.93). DB reports only 2 active large fields, both decoding correctly.
- Whether `dune.markers` is a complete atlas or discovery-driven is unresolved: 99 of 101
  DeepDesert TitaniumOre markers lie within 2 km of the operator's bases, yet the overall marker
  bounding box spans most of the map. May be genuine regional mineral distribution.
- Sandworm spawns, desert mouse, Imperial Testing Stations: no data source found. Parked.
- `dune-resource-scanner` bug: `ValidTransform` rejects exact `(0,0,0)` but accepts denormal
  near-zero floats (~1e-310), producing garbage hits. Needs an issue filed.
- Core bug: `liveMapBases()` filters `coalesce(a.partition_id,0) > 0`, so a base whose instance
  despawned (NULL partition — observed live this session) silently vanishes from the Live Map.

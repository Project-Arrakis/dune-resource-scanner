## Map-wide follow-up (same session)

The operator asked for more data points, and `dune.markers` had grown from 440 to
**7,934** DeepDesert rows across 31 types since session 3. Re-tested map-wide:

- `tools/census.go` scans the whole world in one pass: **59.2M raw triples -> 85,788
  records in 17.3 s at 136 MB RSS**, streaming to disk.
- **64.8% marker coverage (5,144/7,934)** against the shipped 2.8% — a 23x improvement
  on 37x more ground truth. Ore/rock 66–89%, small pickups 14–30%, POIs 0% (expected).
- **Four type-attribution routes ruled out**: the actor chain, all 48 record offsets,
  the object `+0` points at (a bounding box, not a UObject), and memory-address
  clustering (30.9% vs 12.9% chance).
- **Caveat recorded**: the 80,803 unmatched records are *not* all undiscovered nodes —
  median Z 18,058 vs 3,715, and 5.5x the marker count even in the best-explored cell.

A first, naive attempt at relaxing the signature (heap pointer only) was aborted after
it wrote 1.6 GB and reached 10.7 GB RSS. The tool now streams to disk and has a hard
`-maxrecords` cap, which is the actual fix — a wall-clock timeout was never going to
bound memory.

## POI layer resolved (operator-prompted)

The operator reported all Ecolabs discovered without entering any. Verified: **every
POI marker on both maps is `long_range=true` and named** — Cave, Ecolab, Shipwreck,
TaxiService, Sietch, 100% of rows; only `NoIcon` is neither. So POIs are revealed at
range, the DB already holds them all, and **the scanner is not needed for that layer**.
This refines §5's blanket "never an exhaustive atlas" warning, which stays correct only
for resource nodes. It also confirms the census's 0% POI coverage as expected, per §5c
on streamed structure geometry.

Open limit stated: this proves reveal-without-visiting, not that markers populate with
no player on the map, nor how fast they return after a storm.
## `field_id`'s 21-bit ceiling (third-party report, verified)

Another developer reported the decode "fails only past ±1,048,575". Verified:

- **Premise confirmed.** 21 bits signed = ±1,048,575; DD runs to ~±1.27M; **1,237 of
  9,601 real DD markers (12.9%) cannot be encoded**. Bit 63 is unused, so there is no
  escape flag. The spice/flour-sand layer is only proven for the inner ~87% of the map.
- **Conclusion did not reproduce.** Of 19 DD rows whose decode misses memory, **none**
  is near the limit (largest magnitude 803,675), while the most extreme value in the
  set — 1,044,975, on the ceiling — decodes correctly. Un-aliasing by ±2²¹ rescued 0/19.
- **The misses are a scanner under-count, not a decode error**: matched and missed rows
  have indistinguishable decoded-Z distributions, which a wrong decode would not produce.
  Same phenomenon as §8's flour-sand note, now measured across all tiers.
- **Large spice can't be tested here** — DD has only 2 such rows, both decoding to the
  same position, matching a memory hit §8 already flags as a false positive.

Open question for them: is there a Large spice field whose *memory* position exceeds
±1,048,575, and what does its `field_id` decode to? That distinguishes "silently aliases
to a wrong position" (needs a range guard) from "the game never places spice out there"
(needs nothing).

## Correction issued to my own earlier claim

I published that the 80,803 unmatched census records were "NOT all undiscovered nodes",
citing a Z gap of 18,058 vs 3,715. **That was largely wrong** — the gap is mostly
exploration bias (well-explored cells median 4,701 vs 19,317 elsewhere); controlled, it
is 3,559 vs 7,060. A structural signature from the 5,899 confirmed nodes passes **96.4%**
of all records, so there is no structural node/non-node signal. Corrected in
`CONTINUATION.md`, the findings README, and on issue #16.

## Two process notes worth carrying forward

- **A local `timeout ssh` still does not kill the remote process.** A diagnostic
  with an unbounded working set was building a multi-billion-entry map on a host
  with 24 GB free that also runs the live game server. It was caught and killed
  manually before any OOM; game PIDs and free memory were re-verified afterwards.
  Bound the working set *inside* the tool, not just with a wall-clock timeout —
  `diagtype` now refuses to run its offset probe above a hit threshold for exactly
  this reason.
- **A scoring metric can look like a result.** The first type-discriminator search
  reported `pure = 15` — an artifact of `0x0` and a shared vtable satisfying "every
  marker of this type shares a value". Both the wrong metric and the corrected one
  are kept in `findings/`, because the wrong output is plausible enough to be
  believed by the next reader.

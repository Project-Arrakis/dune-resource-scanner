## What was established

### The empty-scan JSON bug — real, fixed

`scanSeeds`/`scanProximity` in `cmd/dune-resource-scanner/main.go` declared their result
slice as `var results []result` (one path explicitly `return nil`), so a zero-match scan
encoded as JSON `null` instead of `[]`. TDD'd: three tests written first, watched fail for
the right reason, then fixed with `results := []result{}`. PR #42, closes #41.

### The `*Pickup` recall-gap claim — re-verified, and it was wrong in a specific way

The prior session's continuation prompt named `RhyolitePickup`/`AzuritePickup` (~67%
recall) as the anomaly against ore types' 66–89%. Re-run against fresh data (12,906
markers, up from 9,601): those two are actually **normal** — they track their Ore
siblings closely. The real, sharp pattern is six *other* types (Titanium, Basalt,
Bauxite, Stravidium, Dolomite, Magnetite Pickup) at 14–28% recall against 70–89% for
their Ore/Rock counterparts. PR #43.

### Hagga's live process is `Survival_1`, not `Overmap`

Running the queued Jasmium discovery test surfaced this. Three scans against `Overmap`
(PID 380152) over ~15 minutes, including one taken while the operator stood directly on a
resource node, all returned the exact same static 112 records — because `Overmap` runs
with 0 connected players and was never the operator's world. `dune.farm_state` showed
`Survival_1` at 1 connected player; scanning that process (PID 2772183) instead returned
91,603 records, matching DeepDesert's scale and the original `2026-08-24-validation/`
numbers (which, it turned out, had used the correct process all along — only this
session's own environment note was wrong). Fixed in
`sessions/CONTINUATION-PROMPT.md`: resolve the live Hagga PID via
`farm_state.connected_players > 0`, never a hardcoded process name. PR #45, closes #44.

### The Jasmium discovery test, finally run

Operator discovered `JasmiumOre`/`JasmiumPickup` ("Jasmium Crystal") in Hagga's "Shoel"
sector — zero prior `dune.markers` rows anywhere, a genuinely new type. Matched against
a census taken on the *correct* process while the operator stood on a node: only 6.1% of
33 markers matched within the standard 1m threshold, but **100% (33/33) had a census
record within 151m**, most within 7–40m. The census does find brand-new nodes; the fixed
1m threshold understates recall for this type specifically. Why the offset is larger than
usual is not established — an operator theory (Jasmium is the only cross-map-exclusive
ore type) was floated, then retracted in the same session (Primrose, a water resource, is
actually the Hagga-exclusive one) — see PR #46.

### The real storm: core hypotheses confirmed, plus something new

Fired at 05:10 PDT, 2026-08-25 — 70 min later than the predicted 04:00, caught unattended
by the windowed watcher on its 15th firing. **Both DeepDesert and Hagga regenerated
simultaneously** (seed 2→3 on both), not just DD as the project's framing had assumed.

Confirmed live, for the first time (previously measured only on one unchanging seed since
2026-08-21):
- DD markers reset to **0**; Hagga collapsed 6,270→684, and every survivor but 22 edge
  cases is `long_range=true` — zero resource-type markers survived either map.
- Census mechanism held structurally with zero players online: DD 84,559→84,130 records
  (-0.6%), Hagga 91,603→91,747 (+0.2%).

New, unexplained: ~39% of DD's resource positions are **byte-identical** pre- to
post-storm (string-exact comparison across 84k records — not a rounding artifact). The
reshuffled 61% is ~2x as likely to carry a known marker and ~7x as likely to be
Ore/Rock-typed when it does. Spatially this splits into three regimes on a coarse
grid: a band that's 90–99.8% stable (likely a map-edge region outside whatever the storm
reshuffles), scattered cells at exactly 0% stable, and a broad "core desert" mixed band.
Root cause not established — two theories floated in
`findings/2026-08-25-storm-regeneration/README.md`, explicitly not extended further.
PR #48, closes #47.

**Still genuinely untested, and it's the actual point of the whole project**: does census
*recall* hold up on the new seed? No ground truth exists yet — DeepDesert has had zero
players since the storm.

### Core issue #479 filed — scanner-packaging design handoff

- **A quick ad hoc command can leak a secret just as easily as a script.** The safe-`ps`
  discipline established in the prior session for committed scripts needs to be a
  standing habit for interactive one-off checks too, not just something to remember to
  apply when writing something that gets committed.
- **A type-mismatch bug in ad hoc analysis code produced a false "0% overlap" result**
  mid-session (comparing CSV string values against un-stringified JSON floats). Caught by
  noticing it contradicted an earlier, correctly-computed 33,047-record overlap — cross-
  checking a surprising result against a previous one caught this before it went into any
  committed finding.
- **A live operator correction, taken immediately.** The Jasmium-exclusivity claim was
  wrong and got fixed the same session, not left to compound — the same discipline this
  project already applies to its own prior sessions' mistakes (see `findings/README.md`'s
  accuracy audit).
